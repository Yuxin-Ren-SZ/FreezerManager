# Handoff note — 2026-09-29, G1.1/G1.3 web tidy-up (#46, worker-2)

The small debts the first three web tasks left in `src/web/`: dead
`app.scaffold.*` i18n keys from G1.1's placeholder page, a `doc/dev/web.md` that
still drew the G1.1 layout, and `src/ui/a11y.ts` — the one axe entry point for
the UI tests — sitting inside the UI kit only because `src/test/` belonged to
another task when it was written. No behaviour change, no new dependency
(`package.json`/`package-lock.json` untouched, so no `lock:deps`). Branch
`feat/46-web-tidy`, PR **#49**.

**Decisions:**

- **The fold is two things, not one, because of a library detail.**
  `vitest-axe`'s `toHaveNoViolations` asserts on axe's *results*, not on a
  container — the container-taking helper it replaced cannot be reproduced by a
  bare `expect.extend`. So `setup.ts` owns both the matcher registration and the
  configured runner, and call sites read
  `expect(await axe(container)).toHaveNoViolations()`. Tests import `axe` from
  `../test/setup` because that is the only module with the configured runner;
  `axe()` called without those options would report `color-contrast` as
  "incomplete" on every node and log a `getContext()` warning per node.
- **`vitest-axe@0.1.0`'s `vitest-axe/extend-expect` does not type Vitest 5.**
  It augments only `declare global { namespace Vi { interface Assertion } }`,
  which Vitest 5 no longer reads, so `tsc` still failed with
  `Property 'toHaveNoViolations' does not exist on type 'Assertion<void, AxeResults>'`.
  The runtime matcher still comes from `vitest-axe/matchers`; the types are
  restated in `setup.ts` against `module 'vitest'`, **augmenting `Matchers`**
  rather than `Assertion` — augmenting `Assertion` fails with TS2428 because
  Vitest 5 ships two incompatible declarations of it. The block says to delete it
  when the library augments `module 'vitest'`.
- **`test.css: true` is documented where it can be found.** With Vitest stubbing
  CSS, `import css from './x.css?raw'` resolves to `''` and
  `tokens.contrast.test.ts` passes *vacuously* — a guard whose failure mode is
  silence. `doc/dev/web.md` now says so next to the setting, not only in the G1.3
  handoff that introduced it.
- **`npm run test` is documented, bare `npx vitest` is called out.** The `test`
  script is what pins `NODE_ENV=test`; verified first-hand rather than restated:
  `NODE_ENV=production npx vitest run src/ui/primitives.test.tsx` → 14 failed,
  `NODE_ENV=production npm run test -- src/ui/primitives.test.tsx` → 14 passed.
- **The two render helpers are recorded as deliberately different.**
  `renderWithProviders()` (one component) and `renderApp()` (whole app) both
  stay; the doc says why, so a later tidy-up does not "deduplicate" them. Same
  for `src/app/stubSession.ts` and `connectionStatus="offline"`, which the issue
  parks on G0.2/G2.1 and the SSE work respectively — this task did not touch
  either.

  fix list). The plant was reverted; no residue in the diff.

**Known limitations / follow-ups:**

- The a11y matcher's type declaration accepts no argument, so
  `expect(container).toHaveNoViolations()` type-checks and only fails at runtime
  ("No violations found in aXe results object"). Tightening it to accept only
  `AxeResults` needs a conditional type; left simple on purpose.
- `src/web/src/ui/Table.tsx:99`'s react-compiler warning is untouched by this
  PR and belongs to whoever next edits `Table`.
- Installing web dependencies on this machine needs a cache inside the checkout
  (`npm ci --cache "$PWD/../../out/npm-cache"`); the shared `~/.npm` cache is
  refused with `EPERM` although it is user-owned. Documented in
  `doc/dev/web.md` troubleshooting.
