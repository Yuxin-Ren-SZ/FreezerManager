# Handoff note — 2026-09-29, bulk check-in/out scan mode (G3.6, worker-1)

Scan a stack of tubes and act on each one: pick an action (**out**, **in** or
**discard**) and an optional reason and volume, then scan repeatedly with a
running session log. Branch `feat/95-scan-mode`, PR **#99**, issue **#95**.

The single scan is the easy half. The issue's two load-bearing criteria are
about the *loop*, and both are the kind that a green happy-path suite cannot
see — so they are decisions in `scanSession.ts` with tests that were watched
failing against a planted violation:

1. **The four outcomes stay four.** Done / no such barcode / wrong state /
   refused are four different next moves for the person holding the tube, and
   three more (`duplicate`, `ambiguous`, `unavailable`) are *not* collapses of
   them.
2. **A duplicate scan is decided by the session.** The second scan of the same
   tube for the same action never reaches the server, so a double-triggered
   scanner cannot double-apply — and the log says so, instead of leaving the
   behaviour to whatever the code happened to do.

**Decisions:**

- **The four outcomes are four values, and the failed request is a fifth.**
  `done`, `not-found`, `wrong-state` and `denied` are separate; `unavailable` is
  "the request never got an answer", because turning "the server is unreachable"
  into "this barcode does not exist" is the worst possible answer at a freezer
  (G3.5's lesson). The classes are the gateway's own: `NOT_FOUND`;
  `FAILED_PRECONDITION` *or* `INVALID_ARGUMENT` (`ConstraintViolation` maps to
  `INVALID_ARGUMENT` in `GrpcErrorTranslation.h`, while the MSW fake answers the
  same condition as `FAILED_PRECONDITION` — both are "wrong state");
  `PERMISSION_DENIED` and `UNAUTHENTICATED`; everything else is `unavailable`.
- **Two more outcomes, both reachable rather than defensive.** `ambiguous`: the
  barcode resolves to more than one sample. `samples` has **no unique index on
  `barcode`** (only `(box_id, position_label)` is unique), so acting on
  `samples[0]` would change a tube the operator is not holding — the probe asks
  for two rows and refuses to guess. `duplicate`: see below.
- **A duplicate is skipped before any request, and keyed `(action, barcode)`.**
  The session remembers the pairs it has already *applied* (only `done` counts,
  so a denied or wrong-state scan can legitimately be retried) and a repeat gets
  a log line, not a second `sample/checkout`. The key includes the action
  because checking a tube out and then checking the same tube back in is the
  reversal the screen documents — a test switches the action and asserts the
  scan is sent again. The barcode is trimmed but never case-folded: the server's
  `barcode` filter is exact, so two barcodes that differ by case are two tubes.
  `New session` clears the guard and the log, and the copy next to the button
  says it does not undo anything.
- **The scan field is read from the DOM at submit time and handed back focused
  with its text selected after every scan** — hit, miss, refusal, failure. Same
  shape as G3.5, and the same failure mode: a state copy can be a keystroke
  behind a scanner's burst, and a field that does not come back focused makes
  the *second* scan type into whatever took the focus. `focusField` selects only
  when the field still holds what was scanned, so characters the operator has
  already typed for the next tube are not overwritten.
- **Scans are serialized through a promise chain.** Two Enter presses in one tick
  (a double-triggered scanner) still produce two log lines in scan order rather
  than two responses racing for the same slot.
- **No free-text fallback, ever.** Scanning `Serum A` — a real sample name — is
  "no such barcode" here, and the test asserts the request carried `barcode` and
  never `query`. An action must not be applied to a fuzzy match.
- **Volume is offered only for check-in** (a check-out consumes nothing, a
  discard takes what is left) and is sent **with its unit**: `CheckoutSampleRequest`
  needs both `volume_used` and `volume_unit` or `SampleServiceImpl::CheckoutSample`
  drops it silently. A negative or non-numeric volume is not sent at all.
- **Auto-submit is optional and off by default**, behind a checkbox with its own
  test for each state, and it never fires for an empty field. When it fires, the
  scanned text is selected first, because with no Enter the operator's next
  keystroke would otherwise append to the previous barcode.
- **There is no undo, so the screen says how to reverse instead.** Check in the
  tube you checked out; a discard is final, so correcting one means creating a
  new sample and recording why in the reason. A test asserts no
  `undo`/`reverse` button exists. The log is not the record — the audit trail is.
- **`aria-live="polite"` on the log**: it is the only feedback a scan gets, and
  a screen reader should hear each line as it is appended.
- **The field is refused (and disabled) without a lab**, and `submitScan()`
  re-checks `labId`, so a scan that arrives before the session loads cannot
  become a `sample/list` for lab `""`.

**Known limitations / follow-ups:**

- **Nothing here is idempotent across sessions.** The duplicate guard is a
  session, as the issue scopes it: a reload forgets it, and the server's state
  machine (`storage::apply_checkout`) is the second, independent reason a
  double-apply cannot land. A test that starts a new session shows both: the
  scan is sent again and the *server* answers `wrong-state`.
- **A barcode that is not unique is refused rather than disambiguated.** The
  screen says to use Lookup; it has no pick list, because a pick list is a mouse
  and the whole point is that the operator never touches one.
- **`G3.3`'s check-in dialog sends `volumeUsed` without `volumeUnit`**
  (`src/features/sample-detail/SampleActions.tsx:217`), and
  `SampleServiceImpl::CheckoutSample` only applies the volume when both fields
  are present — so the typed volume is silently dropped against a real
  `freezerd`, while the MSW fake applies it and keeps G3.3's tests green. Out of
  this issue's scope and reported to the lead as its own finding; this screen
  sends both fields.
- **The `ambiguous` case is unreachable through the shipped UI today** only
  because nobody has created two samples with one barcode; the schema permits
  it (no unique index on `samples.barcode`), which is why it has an outcome
  instead of an assumption.
- **No `?barcode=` deep link.** The top bar's global lookup writes `?q=` for
  `/lookup`; nothing links a term to `/scan`, so the field starts empty.
