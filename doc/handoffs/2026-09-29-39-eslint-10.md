# Handoff note — 2026-09-29, ESLint 10 bump check (#39, worker-3)

**This slice changes no code. It records that the ESLint 10 bump is still not
possible, with the evidence, so the pin does not become permanent by accident.**
G1.1 (#32) pinned `eslint` to `^9` because `eslint-plugin-jsx-a11y` peers `^3 – ^9`
and ESLint 10 makes `npm install` fail with `ERESOLVE`. #39 is the task that
re-checks that pin; issue body and the full evidence comment are on #39.
Branch `feat/39-eslint-10`, base `aa44d6d`.

**Decisions:**

- **The precondition failed, so there is nothing to bump.** Every other ESLint
  package in `src/web/package.json` has caught up (`eslint-plugin-react-hooks@7.1.1`
  and `typescript-eslint@8.70.1` both peer `^10.0.0`; `eslint-config-prettier`
  is `>=7.0.0`; `eslint-plugin-i18next` declares no eslint peer), but
  `eslint-plugin-jsx-a11y@6.10.2` — still the newest release on npm — stops at
  `^9`. The acceptance criterion is the *published peer range*, and it is not met.
- **No forcing, and none was attempted.** No `--legacy-peer-deps`, no `--force`,
  no `overrides` entry, no rule relaxed. The pin exists so that
  `npm ci && npm run check` is reproducible in the `web` CI job; a lockfile that
  only installs because npm was told to ignore the conflict trades a loud failure
  for a quiet one.
- **The pin is now on an end-of-life line, which is new information.** `npm ci`
  prints `npm warn deprecated eslint@9.39.5: This version is no longer supported`,
  and eslint's dist-tags are `maintenance: 9.39.5` / `latest: 10.11.0`. At G1.1
  the pin was "deliberately one major behind"; it is now "the last release of a
  line upstream has stopped supporting". That does not justify forcing the bump —
  it means the re-check below is worth doing rather than deferring.
- **The re-check has a concrete trigger instead of a vague "later".** Upstream
  [`jsx-eslint/eslint-plugin-jsx-a11y#1075`](https://github.com/jsx-eslint/eslint-plugin-jsx-a11y/issues/1075)
  ("Support for ESLint v10") is open and flagged as blocking six other items, with
  two unmerged PRs against it ([#1081](https://github.com/jsx-eslint/eslint-plugin-jsx-a11y/pull/1081),
  [#1079](https://github.com/jsx-eslint/eslint-plugin-jsx-a11y/pull/1079)).
  One command decides it: `npm view eslint-plugin-jsx-a11y peerDependencies`.
- **Both guards were re-proved on the pin, deliberately.** The task asked for
  `i18next/no-literal-string` and the `eslint.config.js` react-hooks assertion to
  be confirmed. There is no bumped config to confirm them against, so the useful
  thing to establish is the **baseline** a future bump has to preserve — see
  Tests. A green `npm run check` after an ESLint major is not evidence on its own.

**Known limitations / follow-ups:**

- **ESLint stays at `^9.39.5`.** The dependency is unchanged and the task's
  outcome is "not yet", so there is no version to verify against ESLint 10 in CI.
- **When the bump does happen, re-run the two probes above, not just
  `npm run check`.** Flat-config `rules` resolution and the
  `reactHooks.configs[...]` lookup are exactly what an ESLint major moves, and
  both failure modes are silent greens — the assertion in `eslint.config.js:23`
  exists because spreading `undefined` would drop every react-hooks rule while
  lint still reported success.
- **The `doc/dev/web.md` line about the pin belongs to the lead**, landed after
  #46 to keep that file single-writer this wave.
