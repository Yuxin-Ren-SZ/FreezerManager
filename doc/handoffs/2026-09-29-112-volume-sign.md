# Handoff note — 2026-09-29, [server] a negative `volume_used` must not add stock (#112, worker-1)

Issue **#112**. Branch `fix/112-volume-sign`, PR to be linked from the issue.
Two commits: `65980ee` (the red test, first) and the fix.

**The bug.** `CheckoutSample` validated that `volume_used` and `volume_unit`
travel as a pair (#100) but never the **sign**. `storage::apply_checkout`
computes `remaining = *sample.volume_value - used` and clamps only at the bottom
(`if (remaining < 0) remaining = 0`), so a negative `used` moves the vial the
other way: -40 µL against a 100 µL vial left it holding **140 µL**, returned it
to `ACTIVE`, and appended a `CheckedIn` chain-of-custody row with
`volume_delta: +40`.

**The semantic chosen: a consumption cannot be negative — refuse it, naming the
field.** The alternative the issue offered (define what a negative volume is
*for*) is rejected, and not because an adjustment entry is implausible — it is
implausible *expressed this way*:

- The action vocabulary is the status machine's (`CheckedOut`, `CheckedIn`,
  `Destroyed`). A "−5 mL check-in" is none of them: it happened to return the
  sample to `ACTIVE`, which is a side effect of `CheckedIn` and not a property of
  an adjustment.
- The audit row would read `CHECKED_IN` with a **positive** delta. A reader of
  the chain of custody cannot tell that from a genuine return without knowing a
  sign convention that exists nowhere else in the record.
- An honest adjustment needs its own event and therefore a new action — a
  `lock:proto` change this issue does not hold.

So the answer is `INVALID_ARGUMENT` naming `volume_used`, and a real adjustment
entry stays available as its own decision with its own event type.

**The zero case — the boundary #112 asks to settle alongside #111.** `0` stays
accepted, and it is distinguishable from "no volume supplied at all": the event
carries `volume_delta: 0` rather than no delta, because `volume_delta` is only
set when `command.volume_used.has_value()`. That distinction is the reason the
rule is `< 0` and not `<= 0`, and both halves are pinned by tests.

**Where the check lives, and why two places.**

| layer | refuses | reports |
|---|---|---|
| `storage::apply_checkout` (`SampleOps.h`) | any negative `Volume` on the command | `ConstraintViolation` → `INVALID_ARGUMENT` via `GrpcErrorTranslation.h` |
| `SampleServiceImpl::parse_volume_used` | any negative `double` on the wire | `ConstraintViolation` → `INVALID_ARGUMENT`, `volume_used: must not be negative` |

The domain check is the *enforcement point*: `apply_checkout` is the operation
that does the arithmetic, so every caller is covered and not only the ones that
arrive over gRPC — which is #112's own argument one layer down. The RPC check
exists because the wire type is a `double` and the cast to the domain's integer
truncates **toward zero**: `-0.5 µL` would otherwise reach storage as a
well-formed `0` and be accepted as a silent no-op. Both are pinned:
`ApplyCheckoutRejectsNegativeVolumeAndLeavesStockUntouched/Sqlite` for the first,
`CheckoutSampleRefusesANegativeVolumeBelowTheUnitGranularity` for the second.

**Why `parse_volume_used` is an extraction rather than an inline `if`.**
`CheckoutSample` is on the list of functions near the cognitive-complexity
ceiling (the board names `UpdateSample` and `prepare_custom_fields`; #100/#107
had already grown this one), so adding a branch was not free. The extraction
lifts the pair check, its branches and the unit-parse `try`/`catch` out of the
handler, which leaves it with **fewer** decision points than before — the new
sign check is the fourth condition of a helper that is well clear of the
threshold. Nothing is suppressed, and no `NOLINT` was added anywhere.

**The web fake mirrors the rule** (`src/web/src/test/fakeApi.ts`), as #100's
did, with two tests in `fakeApi.test.ts`: the negative is refused
(`INVALID_ARGUMENT`, and the vial is untouched with no event), and an explicit
zero is still accepted. The client and the server cannot disagree about the sign
again.

**The issue body was wrong about the clients, and it matters for the client
work.** It says *"No current client sends one — the SPA's control and the scan
screen both produce positive values."* The scan screen does
(`ScanScreen.tsx:184` guards `typed > 0`). The **sample-detail check-in dialog
does not**: `SampleActions.tsx:252` sends `Number(volumeUsed)` whenever the field
is non-empty and finite, and the confirm control is a plain `Button` with
`onClick` inside a `Dialog` — there is no `<form>`, so `min={0}` on the input
(`:286`) is never checked by constraint validation. **A negative was reachable
from the shipped SPA**, which turns "no client does it" from a reassurance into
a description of the tests. `step="any"` on that same input is what makes #111
reachable the same way. No client change is needed for correctness: the server is
the enforcement point and the dialog already renders the returned error.

**Sibling actions.** Neither `CHECKOUT` nor `DISCARD` shares this bug —
`apply_checkout` ignores `volume_used` for both (a check-out consumes nothing; a
discard consumes whatever remains). Both now **refuse a negative volume anyway**,
because the guard runs before the action is dispatched: a malformed field is
malformed whatever the action. The related-but-different finding, **reported and
not fixed**: both actions also silently accept and *discard* a positive volume
the caller sends — #100's shape one action over, and a candidate issue rather
than a third commit here.

**What #111 still owns, and the recommendation.**

- The granularity half: a positive value the domain cannot represent in the
  supplied unit. `parse_volume_used` is where that clause drops in; the fake's
  existing test `truncates the amount before converting, as Volume::from_raw
  does` is the pin that has to change with it.
- **A second face of the same half, found while reading `to_unit` and *not*
  exercised here:** the conversion in `apply_checkout` is
  `command.volume_used->to_unit(*sample.volume_unit)`, and µL→mL divides by
  1'000, so a sample tracked in **mL** receiving `500 µL` becomes `used = 0` and
  the check-in subtracts nothing — the same silent no-op as `0.04 mL`, one layer
  over. It is a code-reading observation, not a test result; it is written down
  because whoever takes #111 needs both faces, and this PR's sign rule is a
  subset of #111's rule rather than a decision against it.
- Recommendation: **refuse, do not convert.** A `double` input needs a rounding
  policy before it can be converted (`0.0006 mL` is 0.6 µL, and rounding that to
  1 µL is a 67 % distortion), and the storage type is an integer count of a unit,
  so "exactly representable, or refused with the finer unit named" is the only
  rule that needs no policy.

Defining the missing builtins on the command line (`-D__builtin_clzg(x,y)=…`,
`-D__builtin_ctzg(x,y)=…`, `-D__GCC_DESTRUCTIVE_SIZE=64`,
`-D__GCC_CONSTRUCTIVE_SIZE=64`) got past the first two and failed on the next
ones, which is the shape of a losing race rather than a workaround — so **no
local complexity number exists for this change**, and the argument for not
tripping the gate is structural: `CheckoutSample` loses the pair check, its
branches and the unit-parse `try`/`catch`, and gains one call. The `clang-tidy`
CI job is the authority; on CI it is a separate, path-gated, cached job.

**Limitations / follow-ups.**

- Non-integral *positive* values still truncate (`0.04 mL` → raw 0). That is
  #111, deliberately, and the fake still pins the truncation so the two cannot
  drift.
- `volume_used` on `CHECKOUT`/`DISCARD` is accepted and ignored (see above).
- A `double` field with an integer domain remains the underlying awkwardness;
  #111 is where it gets a rule.
