# Handoff note — 2026-10-02, G0.1 follow-ups: a pending-MFA session can log out (#62, worker-3)

Issue **#62** carried four non-blocking findings from the security review of PR
#53 (G0.1). Two were already closed before this slice started — the proxy-`Host`
requirement is in `doc/UPGRADE.md` (added with G0.1) and `parse_cookie_header`
was deleted by #53 — so this note covers the two that remained.

The behaviour one is a real, reachable gap: `/api/v1/auth/browser/login` sets
`fmgr_session` **before** the second factor is entered, so a user who abandons
the TOTP prompt holds a credential. `Logout` went through `validate_authed()`,
which throws `MfaRequired` while `!mfa_complete`, and `SameSite=Strict` means no
other page can clear the cookie — the credential was unrevocable from the UI.
Logout is a **de-escalation**, so it is now allowed for a pending session.

The other is an assumption worth writing down: for the unauthenticated login
route the `Origin` check is the only defence, and a **missing** `Origin` is
deliberately allowed. That now has a comment where the next reader will find it.

Branch `fix/62-g01-followups`, PR **#118** (`Closes #62`).

**Changed:**

- `src/server/AuthServiceImpl.cc` — new `validate_token_any_mfa()` in the
  anonymous namespace: `auth.validate_token(bearer)` with no MFA gate.
  `SubmitMfa` now calls it (unchanged behaviour, it used to inline the same
  two lines) and `Logout` calls it instead of `validate_authed()`. The comment
  on `validate_authed()` no longer lists Logout among its callers.
- `src/rest/BrowserSession.cc` — a comment above `if (!req.origin.empty())` in
  `csrf_denial`, recording that a missing `Origin` is deliberate, what it relies
  on, and that `Origin: null` is still refused. **Comment only**, no code change.
- `doc/UPGRADE.md` — one sentence in the G0.1 *Behaviour Changes* section, since
  logout now accepts a request it previously refused.
- `tests/integration/server_integration_test.cpp` — the fixture seeds a second,
  TOTP-enrolled account (`mfa@example.com`); tests
  `LogoutRevokesAPendingMfaSession` and
  `PendingMfaSessionIsStillRefusedByTheOtherSelfManagementRpcs`.
- `tests/integration/rest_gateway_integration_test.cpp` — the same account in
  the REST environment's seed; test
  `PendingMfaLogoutRevokesTheSessionAndExpiresBothCookies`.

**Decisions:**

- **One named helper, not a second bypass.** The issue's third criterion is "the
  change does not widen anything else". Two call sites of `validate_token` would
  have satisfied it, but the exception would then live in two places and nothing
  would say the pair is the whole of it. `validate_token_any_mfa()` is that
  sentence, and `SubmitMfa` was moved onto it as a no-op refactor so the claim
  stays true by construction.
- **`revoke_session` needed no change.** It is idempotent and takes only a
  session id, and `validate_token` already refuses a revoked session — so the
  pending-MFA path revokes exactly like the completed one, and the test asserts
  the *second* call fails as an invalid token rather than as `mfa_required`.
- **Nothing in the REST layer changed.** The logout route's decorator already
  clears both cookies on a 2xx and leaves the failure path alone (clearing on a
  gate rejection would turn a 403 into a logout CSRF). With `Logout` answering
  200 for a pending session, that decorator is enough; the new REST test is what
  proves it end to end.
- **The comment was placed in `BrowserSession.cc`, not the header.** The header
  already explains why the `Origin` half runs without a session cookie; what was
  missing is the *other* half — that an absent `Origin` passes on purpose — and
  that belongs on the branch a reader is looking at. The header's rule list
  ("a present `Origin` must be …") was left alone because it is still accurate.
- **No new test for item 4.** A comment cannot be tested, and the behaviour it
  describes is already pinned: the existing browser-session tests post without
  any `Origin` header and expect the gate to let them through.

**The #78 rebase.** `main` moved under this branch after it was marked ready:
`9ff2c46` (#78) puts all six `auth/*` registrations on
`RpcGate::no_permission_required()` and adds its own permissionless account to
the same two files. The rebase needed two resolutions, both additive:

- `src/server/AuthServiceImpl.cc` — #78's registration comment read "the rest
  need a token and MFA (`validate_authed`)". True when written, false for
  `Logout` after this branch, so it now names `Logout` beside `SubmitMfa` as the
  deliberate not-MFA pair. The registration **values** are #78's, untouched.
- `tests/integration/server_integration_test.cpp` — #78's permissionless account
  is user `...000002`, the id this fixture had given its MFA account. Both
  inserts survived the textual merge, and every test in the file then failed in
  `SetUp()` with **"user id already exists"**. The MFA account moved to
  `...000003`, behind a named `kMfaUserId`.

Two layers changed by #78 could have made the pinning test pass for a *new*
reason, so that was checked rather than assumed. After the rebase
`validate_token_any_mfa()` still has exactly two call sites (`SubmitMfa`,
`Logout`) and `validate_authed()` three (`CreateApiToken`, `ListApiTokens`,
`RevokeApiToken`); and both new tests were shown able to fail by planting the
violation on the merged tree:

- **plant A** — `Logout` back on `validate_authed()`:
  `LogoutRevokesAPendingMfaSession` red with the same
  `mfa_required: MFA required before this operation` as before the rebase, the
  boundary test green;
- **plant B** — `CreateApiToken` widened onto `validate_token_any_mfa()`: the
  boundary test red at its `CreateApiToken` assertion,
  `LogoutRevokesAPendingMfaSession` green.

A registry-gate refusal cannot masquerade as either result: #78's gate answers
`INTERNAL`, while both tests assert `UNAUTHENTICATED` **and** the handler's
`mfa_required` prefix.

Both `clang-format --dry-run --Werror` and the SPDX check pass on the changed
files. `clang-tidy` 17.0.1, run per changed TU and compared against the
unmodified `origin/main` version of the same file, reports **an identical
finding set** in all four — 21 / 19 / 38 / 28 findings, none new (the test file's
baseline rose from 35 with #78's own tests). The local build is the documented
superset of CI's, so that comparison is a hint, not a verdict.

**Known limitations / follow-ups:**

- **The SPA's own pending-MFA logout is not exercised.** The REST route is tested
  end to end here; wiring the sign-in screen's "abandon TOTP" path to it belongs
  to **G2.1**, which owns that screen.
- **`.clang-tidy` locally flags `readability-implicit-bool-conversion` on gtest
  message literals** — the same construct appears eleven times on `main`, whose
  `clang-tidy` job is green, so it is the local-superset artifact rather than a
  CI failure. One new instance was avoided anyway (the new test streams the
  server's own error message instead of a literal); `performance-unnecessary-copy-initialization`
  on `login_resp.session_token()` was fixed.
- **Items 2 and 3 of #62 were not touched** — closed by `7d3ed41` and #53
  respectively, and the numbering was left intact so older notes still line up.
