# Handoff note — 2026-10-20, serve the built SPA from freezerd (#44, worker-1)

A deployment is now one binary plus a directory: when `FMGR_WEB_ROOT` points at
Vite's `dist/`, the REST listener serves the SPA itself, so the browser stays
same-origin (G-arch 5: the gateway sends no CORS headers) and G0.1's `HttpOnly`
cookie is usable end to end. With the variable unset, no static file is served
and the listener behaves exactly as before. The issue also raises the HTTP
request-body cap, which had been a latent CSV-import 413 independent of the SPA.

**Changed:**

- `src/rest/StaticAssets.{h,cc}` (new):
  - `StaticAssetsConfig::from_env(tls)` reads `FMGR_WEB_ROOT` and
    `FMGR_REST_MAX_BODY_BYTES` (default 10 MiB = C-10's
    `max_receive_message_bytes`; a malformed value throws so `main` exits 1);
    `tls` drives HSTS only.
  - `StaticAssets::install` sets `drogon::app().setClientMaxBodySize` always
    (the body cap is needed without the SPA too), then, when a web root is
    configured, registers a catch-all GET handler and a post-handling advice.
  - the advice owns every new response header, so `RestGateway.cc` is
    untouched: the exact CSP (no `unsafe-inline`), `X-Content-Type-Options:
    nosniff`, `Referrer-Policy: no-referrer`, `Strict-Transport-Security` under
    TLS, `Cache-Control: no-store` for `/api/*`, `public, max-age=31536000,
    immutable` for hashed `/assets/*` files and `no-cache` otherwise.
  - the handler serves a regular file under the root, or `index.html` for a
    client-side route; unknown `/api/*` paths (any method) get a JSON 404.
    Traversal is refused twice: `..`/`.`/backslash/NUL segments before the
    filesystem is touched, then `weakly_canonical` containment (so a symlink
    inside the root pointing outside is refused too).
- `src/server/main.cc` — reads the config after the REST TLS decision, calls
  `install`, and logs the served root and body limit once.
- `tests/unit/static_assets_test.cpp`, `tests/integration/
  rest_static_assets{,_tls,_disabled}_integration_test.cpp` plus
  `tests/integration/rest_static_assets_harness.h` (see Tests).

**Decisions:**

- **A missing file under `/assets/` falls back to `index.html`.** The
  acceptance criterion says *any* GET outside `/api/`, `/healthz` and
  `/metrics` returns the shell, so a stale content-hashed asset URL gets HTML
  rather than a bare 404. The advice keys `immutable` off the response being a
  non-HTML 200, so that fallback is never cached as an asset.
- **The body limit is not gated on `FMGR_WEB_ROOT`.** The 413 was a gateway bug
  for CSV imports, not a property of SPA serving: a deployment that never
  serves `dist/` still needs the same ~10 MiB ceiling the gRPC listener has.
- **Three integration binaries.** Drogon's HTTP app is a process-wide singleton
  and `setClientMaxBodySize`/advice registration happen once per process, so
  "SPA on + plaintext + default limit", "SPA on + TLS + 1 KiB limit" and "SPA
  off" cannot share one test executable. They are unlabelled (not
  `grpc_integration`): they start no gRPC server, so the asan preset should
  exercise them.
- **Startup fails on a bad `FMGR_WEB_ROOT`.** A path that is not a directory is
  a deployment error; silently 404ing every page would be worse.

**Tests:**

- `tests/unit/static_assets_test.cpp` — env parsing (defaults, overrides,
  malformed values) and `resolve_path` (file, root, deep link, missing asset,
  `..`, `.`, backslash, NUL, symlink escape).
- `tests/integration/rest_static_assets_integration_test.cpp` — index/asset/
  deep link, JSON 404, `no-store` on known API responses, health/metrics
  precedence, raw and percent-encoded traversal (`%2e%2e`, `%2f`, `%5c`),
  symlink escape, all headers, and a 2 MiB import body.
- `tests/integration/rest_static_assets_tls_integration_test.cpp` — HSTS under
  TLS; 2 MiB rejected with 413 when `FMGR_REST_MAX_BODY_BYTES=1024`.
- `tests/integration/rest_static_assets_disabled_integration_test.cpp` — unset
  `FMGR_WEB_ROOT`: no files, no new headers, framework 404 unchanged.

The three HTTP binaries set `ASAN_OPTIONS=detect_container_overflow=0` in
CMake: Drogon is prebuilt without sanitizer instrumentation and its
process-exit teardown trips a container-overflow report inside its own
`std::unordered_map` (uninstrumented drogon fills it, instrumented libc++
headers annotate it). ASan still covers the request path and every other
check; the pure config/path logic also runs in `freezermanager_rest_unit_tests`
without the suppression.

Live smoke run of the built `freezerd` on slot-1 loopback ports
(`127.0.0.1:50061`/`18081`, stub `dist/`): `GET /` and a deep link → 200
`index.html` with `cache-control: no-cache` and the CSP/nosniff/referrer
headers; `/assets/app-abc123.js` → `text/javascript` + `immutable`; unknown
`/api/v1/*` → 404 JSON + `no-store`; `/healthz` and `/metrics` → 200;
`--path-as-is` `/../secret.txt`, `/%2e%2e/secret.txt` and
`/assets/%2e%2e/%2e%2e/secret.txt` → 404 without the canary; a 2 MiB POST to
`/api/v1/sample/import` reached the gateway (400 on the JSON body, not 413).
Restarted without `FMGR_WEB_ROOT`: `GET /` and `/api/v1/*` → Drogon's HTML 404
with no CSP, and a 2 MiB body was still accepted (not 413).

**Known limitations / follow-ups:**

- `setClientMaxMemoryBodySize` is left at Drogon's 64 KiB default: bodies above
  it spill to a temp file and still reach the gateway, so this is a
  performance knob, not a limit.
- Only GET is served from the disk (HTML, JS, CSS, fonts, images). Other verbs
  to a non-API path get 404; nothing in the SPA needs them.
- The SPA's real `dist/` was not built here (no web change in this slice); the
  smoke run and tests use a stub web root, as the issue's test plan specifies.
- #133 (G4.1) will add a route to the same gateway and rebase on this; the
  fallback regex only claims paths no exact handler matched, so a new
  `/api/*` route keeps precedence automatically.
