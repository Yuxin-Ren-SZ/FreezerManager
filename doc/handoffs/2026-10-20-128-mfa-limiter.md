# Handoff note — 2026-10-20, no TODO ID — SubmitMfa brute-force limit + token/MFA RPCs in the data-tier limiter (#128, worker-2)

`AuthService/SubmitMfa` was the one step between a leaked password and a PHI
system, and nothing slowed guesses down. The six `TokenAndMfa` RPCs
(`CreateApiToken`, `ListApiTokens`, `RevokeApiToken`, `ListSessions`,
`RevokeSession`, `ListLabs`) were also outside the process data-tier rate limiter
that every `authorize()`-gated RPC passes through. This slice closes both gaps
without changing the credential-rule enforcement #119 landed.

**Measurement (the issue asked for it first).** `LocalAuthProvider::verify_totp()`
only compares the code and sets `mfa_complete`; it has no attempt counter,
lockout, or replay guard. The login token bucket in `AuthServiceImpl` is entered
by `Login` alone, and `AuthMiddleware::authenticate()` did not consult the
process data-tier gate (only `authorize()` did). The six RPCs were therefore an
omission, not a documented scope choice — the previous `authenticate()` comment
claimed the data tier covered all authenticated endpoints. Exposure: an attacker
holding a valid password gets a pending-MFA session from `Login`, then may guess
the six-digit TOTP without limit; the ±1-step window makes 3 of 1,000,000 codes
valid per attempt, so at machine speed a hit is minutes away, and success is a
full session with the account's PHI access.

**Changed:**
- `src/server/AuthServiceImpl.{h,cc}` — `mfa_limiter_` (token bucket, capacity 5,
  refill 1/minute) checked in `SubmitMfa` after the token gate and before
  `verify_totp()`, keyed by `user:<id>`. Constants
  `k_mfa_rate_capacity` / `k_mfa_rate_refill_per_sec` are public so tests track
  the handler. Refusal is `RESOURCE_EXHAUSTED` (`auth::RateLimited`, REST 429).
- `src/rpc/AuthMiddleware.{h,cc}` — `authenticate()` applies the process
  data-tier limit for `CredentialRule::TokenAndMfa`; the duplicated bucket check
  moved into a private `apply_data_tier_limit()` helper shared with
  `authorize()`. Header docs updated: steps renumbered, the data-tier section now
  states which rules it covers.
- `tests/unit/auth_middleware_test.cpp` — data-tier tests for `authenticate()`
  and the `TokenOnly` exemption, plus an RAII guard that uninstalls the
  process-global limiter.
- `tests/integration/server_integration_test.cpp` — `SubmitMfa` burst and
  mistyped-then-correct tests; a `TinyDataBudgetServerTest` fixture (overrides a
  new `make_server_options()` hook) drives all six RPCs against a one-request
  data bucket.

**Decisions:**
- **Key the MFA budget by user, not by session or bearer token.** Re-login with
  the same stolen password would otherwise mint a fresh budget; the test
  `SubmitMfaBurstIsRateLimited` asserts the second session is still refused.
- **Capacity 5 / refill 1 per minute.** Five immediate attempts cover a typo and
  retries; a successful guess after five failures must wait a minute. This is a
  deliberate rate limit, not a permanent lockout — a permanent one needs durable
  state and an unlock path.
- **`TokenOnly` stays outside the data-tier budget.** `SubmitMfa` has its own
  limiter, and `Logout` only removes authority; making either fail because a
  data-traffic bucket drained would be a worse bug than the one being fixed.
- **`WhoAmI` is covered too.** It is the seventh `TokenAndMfa` RPC (added by #140
  after #119 filed #128); the rule-based step covers it automatically, and the
  six-RPC test is the issue's named list, not a hard-coded allowlist.
- The budget is process-local, like the existing login and data-tier limits. No
  schema migration is involved.

**Known limitations / follow-ups:**
- The MFA budget is per process and in memory: a restart resets it, and a
  multi-process deployment would have one budget per process (same as the
  existing login and data-tier limits). Durable per-user lockout would need a
  migration and a `lock:migration`, so it is deliberately out of this slice.
- TOTP counters are not recorded, so a code observed within its 90-second window
  can start a second session (standard TOTP replay exposure). Successful
  verification marks the session complete, so it cannot be replayed on the same
  session. If replay hardening is wanted, it is a new issue.
- The login limiter remains per source IP, not per account. This slice does not
  change it.
